Lunch & Learn

Welcome. A Lunch & Learn is a format: one design question your team keeps debating, every answer to it built for real, and an hour to try them side by side.

The idea comes from Sam Peterson's Lunch & Learn, the original site of this kind: interactive lessons that run competing approaches side by side in the browser. This site follows its lead and its look.

These pages are written for senior engineers and architects. You will know many of these trade-offs from experience; here you can measure them. Nothing here is mocked. Every service, database and queue is running, and every number is timed while you watch.

Pick a topic and press play. Slow a service down, switch one off, and see how each pattern behaves. If a question from your own work comes to mind, build a topic for it with the Lunch & Learn kit, a template repository with this structure and style, and share it the same way.

🧩 Federated Services vs Event-Driven Projections

Most companies split their software by domain: one service owns people, another owns jobs, another owns security badges, each with its own team and database. A single screen often needs all three.

Federated services ask every owning service at the moment of the request and combine the replies. Event-driven projections keep a combined copy up to date from each service's events and answer from that.

These lessons run both against the same data and measure what each costs in speed, freshness and failure. The source for this topic is on GitHub: each pattern in its own folder, one plain file per service.

  • One question, three services

  • When the bus stops

    Stop the broker or the consumer. Writes still succeed; the read side falls behind, then catches up.

⚛️ Is useEffect a Code Smell?

"useEffect is a code smell" overstates a narrower point. Effects are the right tool for syncing with something outside React, and a source of bugs when used as a general "when X changes, do Y".

These lessons run each misuse next to its fix, in real React against a real server: a fetch race, a stale reset, an order placed twice and a request waterfall. Then they measure how rare the race is on wired, office and mobile connections, and what that means at your scale.

The source for this topic is on GitHub and runs on your laptop with npm install and npm run dev.

  • Start here: the claim and where it comes from

    What effects are for, where the slogan comes from, and every term the lessons use.

  • Typing faster than the server

    Search as you type. An older answer lands last and the page shows results for the wrong query.

  • Switching users

    Reset state in an effect and one commit shows the previous user's draft. Every time.

  • The order placed twice

    Place an order from an effect, leave, come back, and count the orders on the server.

  • Fetch, render, fetch again

    A parent fetches, renders a child, and the child fetches. Time the waterfall.

  • How rare is the race?

    Run hundreds of real keystroke pairs on a wired, office or mobile profile and count stale results.

  • So is it a code smell?

    Maintainability, the AI argument, a scorecard, and what the numbers mean at your scale.
