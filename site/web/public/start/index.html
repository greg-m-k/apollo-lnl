Federated Services vs Event-Driven Projections

Two patterns for the same problem: a screen needs data that lives in several services. This page explains the problem and both patterns from the ground up. The lessons after it let you run them: both patterns are really running, nothing is mocked, and the source is on GitHub.

Domains and domain services

A domain is one area of the business that has its own vocabulary, its own rules and its own data. In this demo there are three. HR knows who a person is: name, email, hire date. Employment knows their job: title, department, salary. Security knows their badge: number, access level, clearance. The word "active" means something different in each: still employed by the company, still in this job, badge not revoked. That difference is the sign of separate domains.

A domain service is the one service that owns a domain's data. It has its own database, and it is the only thing allowed to change that data. Everyone else must go through its API. One team owns it. The HR service owns the persons table, the Employment service owns employees, the Security service owns badge_holders, and none of them can see the others' tables.

Companies split systems this way so teams can work without waiting on each other. Security can change how clearances work and deploy on a Tuesday without a meeting with HR. A bad release in one service cannot corrupt another's data. Each database can be shaped, scaled and secured for its own job. The salary column is not sitting in a database that the badge-printing code can read.

The problem

Screens do not respect those boundaries. A reception desk wants to see, for the person in front of it, their name, their job title and their badge's access level. That is one question with three owners. No single service can answer it, and because each service has its own database, nobody can write a SQL join across them.

Something has to combine the three. The two patterns differ on when the combining happens: at the moment someone asks, or ahead of time.

Federated services

Combine at the moment of the request. Each domain service publishes a schema describing the data it owns. A router merges those schemas into one, so clients see a single API. When a query arrives, the router works out which service owns each requested field, calls those services, and stitches the replies into one answer.

client ──▶ router ──▶ HR          (who is person-001?)
              ├────▶ Employment  (job of person-001?)
              └────▶ Security    (badge of person-001?)
           ◀── one combined answer

This demo uses GraphQL Federation, the most common form of it. Its terms:

Subgraph
One domain service's GraphQL API: the types and fields it owns.
Supergraph
All the subgraph schemas composed into one. Clients query this.
Router (or gateway)
The service clients call. It holds the supergraph and does the combining. It owns no data.
Entity and key
A type that more than one subgraph contributes to, such as Person, and the field that identifies it, id. HR defines Person. Employment adds an employee field to it; Security adds badge. Given only a person's id, each can supply its part.
Query plan
The router's list of calls for one query, and their order. Here: ask HR for the person first, then, with the id HR returned, ask Employment and Security at the same time.

What you get: the answer is always current, because every field comes from its owner right now. Writes are simple: a change goes to the owning service and the next read sees it. There is nothing to keep in sync.

What it costs: every read depends on every owner. The answer is as slow as the slowest chain of calls, and if one service is down, its part of the answer is missing.

Event-driven projections

Combine ahead of time. Whenever a domain service changes its data, it also announces the change as an event: a record of something that happened, such as "PersonCreated" or "BadgeRevoked". A separate consumer listens to all the events and keeps its own copy of the data, already shaped for the screens that need it. That copy is a projection. A screen asks one query service, which reads the copy.

write:  client ──▶ HR ──▶ its database + outbox
                          └─▶ topic ─▶ consumer ─▶ projection
read:   client ──▶ query service ──▶ projection (one local read)

Its terms:

Event
A fact, in the past tense, published by the service that owns it. In this demo each event carries the full current state of the thing that changed.
Broker and topic
The messaging system that carries events (Kafka in the original, Cloudflare Queues here), and a named stream of events within it, one per kind of thing.
Outbox
A table in the owning service's own database. The service writes the data change and the event into its database in one transaction, and a small relay publishes the event afterwards. Without this, a crash between "save the row" and "send the event" would lose the event for good.
Consumer
The service that reads events and updates the projection. The broker may deliver an event twice, so applying the same event again must change nothing. That property is called idempotent.
Projection (or read model)
A copy of other services' data, built from their events and stored in the shape a reader wants. It can always be thrown away and rebuilt from the events.
Eventual consistency
The copy is correct, but slightly late. After a write there is a short gap, usually well under a second, before the projection shows it.

What you get: reads are one local lookup, fast and steady, and they keep working when the owning services, or even the broker, are down.

What it costs: the answer can be out of date, so "write, then immediately read" needs thought. There are more parts to build and run: outbox, relay, broker, consumer, and a second database.

What the lessons show

Both patterns run here against the same three domains and the same five seed people. Each lesson asks both the same thing.

  1. One question, three services: the read path. See the router's query plan as a timeline, slow one service down, and compare with a single local read.
  2. When a service goes down: switch off HR, Employment or Security and see which answer survives, and in what state.
  3. Write, then read: create a person in both and read straight back. Follow one event through outbox, relay, queue, consumer and projection, with the time each step took.
  4. When the bus stops: stop the broker, or the consumer, and keep writing. Watch the owner's data and the projection drift apart and meet again with nothing lost.
  5. So which one?: measure both yourself and read the tradeoffs with your own numbers.
  6. How this runs on Cloudflare: what each part is built from.
Federated services buy freshness and simplicity and pay with coupling at read time. Event-driven projections buy fast, independent reads and pay with staleness and more machinery. Many systems use both: federate the few fields that must be live, and project the rest.
